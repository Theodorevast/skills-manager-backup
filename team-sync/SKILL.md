# 三家配合：共享任务板

用户给 Claude、Codex、Grok 都开了订阅，要求三家配合，谁都可以是发起方。三家看不到彼此的聊天，**唯一的共同事实是项目文件夹里的任务板**（`<项目>/.agent-tasks/`）。一个不在任何沙箱里的"传达员"服务（开机自启）负责把任务单送到对应的 AI 并把结果写回。

命令是 `team`（下文写作 `TEAM`）。找不到这个命令时用完整写法：

```bash
python3 "$HOME/.local/opt/agent-team/team.py"
```

`--from` 填你自己：`claude`、`codex` 或 `grok`。`--project` 填项目的绝对路径。这些命令只读写项目里的文件，在任何沙箱里都能跑。**不要自己去启动另一个 AI 的命令行**，沙箱会拦，也会绕过任务板。

**适用范围**：不限游戏。项目只要放在 `~/Games/<名字>` 或 `~/Projects/<名字>` 下就能用（传达员只监视这两个文件夹，清单在 `~/.config/agent-team/roots`）。放在别处的项目，`post` 会直接报错并说明原因；这时告诉用户，不要硬派。

## 每次开工先做

```bash
TEAM board --project "<项目>"
```

看三样：进行中的任务、被占用的路径、最近的日志。别人占着的路径不要碰；与你要做的事重复的任务不要再派。

## 自己要改文件之前

```bash
TEAM claim --project "<项目>" --from <你> --paths "src/ui/**,index.html" --note "在做什么"
```

返回"冲突"就不要改，换别的活或等对方做完。改完立刻：

```bash
TEAM release --project "<项目>" --from <你>
```

## 把活交出去

1. 把任务写成一个文件（放在 `<项目>/.agent-tasks/` 下即可）。对方看不到你的聊天，任务单必须自成一体，写清六件事：背景一两句；要做什么；能读能改哪些路径；能不能联网、能不能调用付费生成；怎样算做完；交回的格式和长度。路径放进引号。
2. 派发。`--to` 填某一家，或填 `others` 同时派给另外两家：

```bash
TEAM post --project "<项目>" --from <你> --to others --title "一句话标题" --task-file "<任务单>" --id <短名字>
```

要对方改文件就加 `--write --paths "<它能改的路径>"`。只读任务不加。写任务的路径与别人占用的路径重叠时，任务会停在 `blocked`，对方放开后自动开始。

3. 取结果（`--to others` 时任务名会带上 `-claude`、`-codex`、`-grok` 后缀）：

```bash
TEAM wait --project "<项目>" --id <名字1>,<名字2> --show
```

只读任务通常 10–60 秒，复杂的几分钟。任务结束时用户会收到系统通知；用户也可以在浏览器打开 http://127.0.0.1:8765 看所有项目的任务板（`TEAM web` 会替他打开）。状态不是 `done` 时读 `<项目>/.agent-tasks/<名字>/` 里的 `meta.json` 和 `raw.log`，不要原样重派。`post` 时如果提示"传达员服务没有在运行"，告诉用户，由用户启动。

## 被派出去的那一家能做什么

任务在无界面会话里跑。三家都被系统级沙箱限制住：**只读任务改不了项目里任何文件；写任务只能改一份独立副本**。

| | 终端命令 | 联网 | 上限 |
|---|---|---|---|
| Codex | 能 | 写任务里不能 | 900 秒 |
| Grok | 能 | 能 | 900 秒、40 轮 |
| Claude | 写任务里能，只读任务里不能 | 能 | 900 秒、40 轮 |

写任务是这样进行的，写任务单时要知道：

- 对方拿到的是**项目的一份副本**，在副本里改。任务单里用相对路径；写了项目的绝对路径也会被自动换成副本路径。
- 做完后系统核对它实际改了哪些文件。全部在 `--paths` 之内，而且这些文件在原项目里没有被别人动过，才把改动一次性带回原项目（全有或全无）。
- 状态 `out_of_scope`：改了范围外的文件，**什么都没带回**。`conflict`：任务期间原文件被别人改了，没带回。`apply_failed`：带回时出错，一般已还原；理由里若写着"有文件没能还原"，立刻告诉用户，不要自己动那些文件。`no_change`：对方说做完了但范围内什么都没改。`interrupted`：被中断，改动没进项目。这些情况副本都保留着（14 天），理由里有路径；由发起方看过后决定重派还是手工取用，并告诉用户。
- `done` 的任务也要读一眼理由：文件夹自身的变化（权限、新建的空文件夹）不会带回，有的话理由里会写。成功带回的副本另外保留 3 天。
- 对方在副本里装的依赖、跑出来的构建产物（`node_modules`、`dist`、`.godot` 等）默认不会带回。**确实要带回构建产物，就在 `--paths` 里把那个目录写明**（例如 `--paths dist/`）。
- 想让对方用某个 skill，在任务单里写出它 `SKILL.md` 的绝对路径让对方去读，不要指望它自动触发。

## 跨家评审一律走任务板

让另一家审代码、审设计、挑刺，都用 `TEAM post`，不要用本家的子代理冒充"另一家"，也不要用 `gstack-codex` 之类直接调对方命令行的办法（那会绕过任务板，别人看不到）。

多轮互评按这个流程，最多 2 轮：

1. 作者做完，`post` 一个只读评审任务给另一家。任务单写清：做了什么、需求是什么、看哪些文件；要求按"致命 / 重要 / 可优化"三级列问题，每条给证据。
2. 作者取回意见，**先核实再改**：不成立的可以有理由地反驳，不要客套式全盘接受。只有"致命"和"重要"进入修改；"可优化"用 `TEAM note` 记下即可。
3. 复审任务只判每条"已解决 / 未解决"并指出新引入的问题，不重新全评。
4. 2 轮后仍有分歧，由发起方裁决并记日志；拿不准的提给用户。
- 每一轮用新的任务名（如 `r1-review`、`r1-fix`、`r2-recheck`），同名任务会直接返回旧结果。

## 值得别人知道的事，记一笔

```bash
TEAM note --project "<项目>" --from <你> --text "决定用 Vite，开发端口 5220"
```

## 什么活给谁

| 谁 | 适合 |
|---|---|
| Grok | 额度最宽裕。重复的、量大的、不要紧的活优先给它：调研找参考、批量检查素材、整理清单、对别人的结论做独立复核、画面和手感的第二意见 |
| Codex | 独立审代码和挑刺；边界清楚的独立模块；把视觉参考整理成美术规范；自动化验收脚本 |
| Claude | 和用户对话、定方案、拆任务、集成；游戏项目里操作 Godot 和 UE 编辑器 |

用户已给默认授权：不必每次问"要不要派给谁"，自己判断着派，事后在汇报里说明派了什么、结果如何。用户不熟技术细节，需要用户做决定或亲自操作的事要主动提醒。

## 不变的规矩

- 同一个文件、同一个编辑器，同一时间只让一家动。
- 付费生成（生图、生模型、生视频等）只在用户明确授权的任务里提交；派出去的任务单里要写明"不得调用付费生成"，除非用户已授权这一项。
- 提交和推送只在用户要求时做。
- 被派来的任务是只读时，系统会真的拦住写入；不要想办法绕过。
- `~/Games/afterglow-grand-prix` 冻结中：不跑、不改、不拉，也不要对它派任务。
